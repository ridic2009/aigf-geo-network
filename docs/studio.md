# MiniCMS Studio

Studio — редактор сайтов поверх существующего Cecil/Twig-движка. Публичные сайты остаются статическими. PHP нужен рабочему пространству редакции и процессу сборки.

## Быстрый запуск на этом компьютере

Из корня проекта:

```powershell
composer install
php scripts/studio.php serve
```

Откройте **http://127.0.0.1:8787**. При первом локальном запуске создайте администратора. В разделе **Команда** добавьте авторов и редакторов и назначьте им ID доступных сайтов. Пароли — от 12 до 72 байт. Данные сохраняются в `.studio/`, каталог исключён из Git.

Для работы нужны PHP 8.2+ и расширения `mbstring`, `intl`, `gd`, `dom`, `simplexml`, `fileinfo`, `zip`; для деплоя — также `curl`, SSH и POSIX shell. Node не нужен приложению; он используется только в браузерных тестах.

В отдельном терминале можно обработать одно задание **без отправки на сервер**:

```powershell
php scripts/studio.php worker
```

Такой запуск собирает сайты и создаёт архив. Материал останется «Одобрено», а задание получит «Собрано — без деплоя». Для следующей попытки выпуска нажмите «Опубликовать» ещё раз.

## Редакционный процесс

```text
Черновик → На проверке → Одобрено → очередь → Публикуется → Опубликовано
                                                    └→ Ошибка публикации
```

| Участник | Возможности |
| --- | --- |
| Автор | Читать назначенные сайты, создавать материалы, править свои черновики, отправлять на проверку, создавать предпросмотр |
| Выпускающий редактор | Править материалы назначенных сайтов, возвращать на доработку, одобрять конкретную ревизию, ставить её на публикацию |
| Администратор | Дополнительно управлять пользователями, сайтами, моделями и оформлением |

Права проверяет сервер на каждом запросе. Подмена `status`, номера ревизии или вызов API вручную не даёт автору права одобрения. Сохранение после одобрения снимает его; устаревшее задание отменяется. Отзыв роли одобрившего редактора отменяет ещё не начавшееся задание.

Одобрение привязано к ревизии **материала**. Настройки, общие данные и шаблоны принадлежат доверенному администратору: изменение общего компонента попадёт в следующую сборку. Это не система согласования каждой правки всего репозитория.

Черновик Studio не переписывает опубликованный Markdown. Worker создаёт отдельную копию исходников, проверяет контент, строит сайты и архивирует результат. Только успешный деплой со smoke-проверками даёт состояние «Опубликовано» и обновляет исходники. При ошибке есть сообщение, ссылка на материал/поле и журнал задания. Ошибки сетевого подключения или сервера показываются на уровне задания: у них нет поля контента, которое можно исправить.

Предпросмотр строится настоящими шаблонами, доступен только создавшему его пользователю, требует авторизации и истекает через час. Скрипты внутри него отключены. Папки предпросмотров автоматически пока не удаляются.

### Граница прав Studio

У авторов и выпускающих редакторов должны быть **только учётные записи Studio**. Прямой доступ на запись в файловую систему рабочего пространства или к SSH-ключам публикации позволяет обойти весь процесс согласования.

Studio — единственный редактор и единственный публикатор. Стороннего CMS и CI в схеме нет: рабочее пространство и есть источник правды, его версионирует сама Studio, а внешняя копия уезжает на второй сервер (см. «История правок» и «Резервные копии»).

При обновлении кода движка остановите worker, снимите резервную копию, затем обновляйте.

## Сайт, страна и язык

В **Создать сайт** задаются независимо:

- `site.id` — уникальный ID и каталог контента, например `brand-two-us-en`;
- `brand` — бренд;
- `market` — рынок/страна, например `us`;
- `language`, `locale`, `hreflang` — язык, форматирование и язык/регион для поиска;
- `translation_group` — группа сайтов одного бренда, между которыми допустимы hreflang-ссылки;
- домен, модель страниц и тема.

Два бренда могут работать в одной стране. Для разных брендов используйте разные группы переводов. Переводы страниц связывает одинаковый `translation_key` внутри группы; staging-сайты исключаются из hreflang.

Новый сайт получает отдельный `content/<id>/`, черновик главной и пустое меню. Он создаётся тестовым, с запретом индексации и выключенным из общей сборки. Сначала заполните и опубликуйте главную, подготовьте домен/HTTPS, затем включайте сайт. Языковые версии сейчас размещаются на отдельных доменах/поддоменах; схема `example.com/en/` не реализована.

Существующие `config/geos/*.yml` совместимы с новой системой. `config/sites/*.yml` имеет приоритет; начальные файлы наследуют старые GEO. После сохранения настроек Studio записывает самостоятельную конфигурацию сайта.

## Темы, блоки и SEO

Есть три темы: `classic`, `editorial`, `midnight`; можно менять акцентный цвет. Темы задают цвета, ширины и скругления в `config/themes/`. Это варианты оформления общего набора шаблонов. Для совершенно нового расположения элементов добавьте доверенный Twig-шаблон.

Доступные блоки: **текст, изображение, CTA, подборка продуктов, FAQ, таблица**. Их можно добавлять, удалять и переставлять стрелками. Поля блоков проверяются; FAQ попадает также в JSON-LD. Изображения PNG/JPEG/WebP загружаются из редактора. Текст поддерживает Markdown, произвольный HTML автора не исполняется.

SEO-поля: title, description, основной запрос, настройки индексации, canonical, социальные заголовки и изображение, обложка, хлебные крошки. При отправке на проверку ошибки ведут к соответствующему полю. Необязательные SEO-поля можно оставить пустыми; canonical обычно вычисляется автоматически.

В настройках сайта доступны тексты интерфейса и меню. Пункт меню ссылается на стабильный ID страницы (`about`, `reviews/example`, `index`), а URL вычисляется из маршрута. Ссылка на неопубликованную страницу пока не отображается.

## Товары и партнёрские ссылки

Раздел **Товары** — каталог, общий для всей сети. Одна запись описывает продукт целиком: название, сайт, логотип, рейтинг, возможности, цена по умолчанию и партнёрская ссылка по умолчанию, а дальше — вкладка на каждый рынок с его доступностью, описанием на местном языке, ценой и своей партнёрской ссылкой. Пустая цена или ссылка на рынке означает «взять значение по умолчанию».

На диске это по-прежнему два файла: `data/products/<id>.yml` для того, что видит читатель, и `data/affiliates/<id>.yml` для того, куда ведёт кнопка. Шаблоны читают их через разные хелперы, и файл со ссылками можно заменить редирект-сервисом, не трогая ни одного шаблона. В интерфейсе это одна карточка, потому что редактор думает о них вместе.

Обзоры и рейтинги ссылаются на товар по ID, а не копируют значения. Поэтому:

* в списке видно, на скольких страницах используется товар, а на карточке — на каких именно;
* товар, на который ссылается хоть одна страница, удалить нельзя;
* рынок без цены и без ссылки помечен в списке жёлтым — так видно пробелы после добавления новой страны.

Писать в каталог может только администратор: опечатка в цене здесь — это опечатка в цене на всех доменах сети.

**Когда изменения попадут на сайт.** Пока `affiliate.redirect_base` в `config/common.yml` пуст, ссылки вшиты в HTML, и цена, и ссылка появятся только при следующей сборке и публикации. Если задать `redirect_base`, ссылки станут вида `go.<домен>/<товар>/<гео>`, а адрес назначения будет жить в карте Nginx из `scripts/redirect-config` — тогда смена партнёрской ссылки применяется без пересборки страниц. Цены рендерятся в HTML в любом случае и всегда требуют сборки.

### Собственная тематика

Схемы находятся в `config/models/`. Одна конфигурация определяет типы страниц, формы Studio и правила валидации. Пример второй тематики — `services.yml`, каталог услуг.

```yaml
label: Каталог специалистов
types:
  homepage: {label: Главная, section: null, layout: index, fields: {}}
  static: {label: Страница, section: null, layout: _default/page, fields: {}}
  expert:
    label: Специалист
    section: experts
    layout: _default/page
    fields:
      specialty: {label: Специализация, type: string, required: true, display: true}
      experience: {label: Стаж, type: number, minimum: 0, display: true}
```

Сохраните как `config/models/experts.yml` и выберите модель в настройках сайта. Поля с `display: true` выводятся базовым шаблоном. Поддерживаются `string`, `text`, `number`, `boolean`, `date`, `url`, `image`, `product`, `object`, `list`, набор допустимых значений `options` и вложенные схемы. Списки/объекты для сложного отображения выводите собственным Twig-шаблоном. Новые виды блоков добавляются в `config/blocks.yml` и `engine/layouts/blocks/`.

Смена модели существующего сайта отклоняется, если она не поддерживает типы его исходных страниц.

После добавления модели или сайта имеет смысл прогнать проверки:

```sh
php scripts/validate.php
```

## Смена URL

При публикации нового `slug` прежний адрес опубликованной страницы становится alias с HTTP **301**. Внутренние Markdown-ссылки и URL блоков обновляются; стабильные ID меню и переводов сохраняются.

Настройки → **Адреса разделов** меняют префикс раздела. Перенос сохраняет старые адреса страниц и индекса раздела, обновляет внутренние ссылки, снимает одобрение черновиков сайта. При конфликте адресов конфигурация и контент возвращаются к предыдущему состоянию. Старые aliases видны в исходниках; автор не может произвольно подменять их.

Циклы, занятие существующего адреса и редиректы на неопубликованные страницы блокируют сборку. Цепочки разворачиваются сразу на конечную страницу. Nginx сохраняет параметры запроса. Фрагмент `#section` обрабатывается браузером.

Произвольные дополнительные переносы администратор может задать в `config/sites/<id>.yml`:

```yaml
redirects:
  /old-article/: /new-article/
```

Смена домена сохраняет `previous_domains`. Перегенерируйте и установите vhost-файлы, оставьте DNS и действующие TLS-сертификаты старого домена. Одна запись в Studio не перенастраивает DNS, сертификаты и Nginx на VPS.

## Публикация на сервер

Нужны два разных назначения:

- **Studio/build host:** постоянная рабочая копия, PHP, Composer-зависимости, состояние `.studio/`, процесс worker;
- **сайты:** Nginx и готовые статические файлы; могут находиться на отдельных VPS.

### Размещение Studio

Для production используйте Nginx + PHP-FPM, отдельный hostname и HTTPS. Корень сайта — строго `studio/public/`, не весь репозиторий. Все запросы, включая `/api` и `/preview/...`, направляйте в единственный `index.php`; приложение само выдаёт два публичных ресурса и авторизованные previews. Не разрешайте выполнение произвольных PHP-файлов по URL.

В HTTPS-vhost пример блока (замените пути/socket):

```nginx
root /srv/minicms/studio/public;
client_max_body_size 6m;
location / {
    include fastcgi_params;
    fastcgi_param SCRIPT_FILENAME /srv/minicms/studio/public/index.php;
    fastcgi_param HTTPS on;
    fastcgi_pass unix:/run/php/php8.3-fpm-minicms.sock;
    fastcgi_read_timeout 180s;
}
```

FPM-пул выделите под сервисную учётную запись `minicms`. Ей нужны чтение кода и зависимостей, запись в `.studio`, `.cecil`, `.cache`, `dist`, `content`, `config/sites`, `static/images/content`. Worker и FPM должны иметь совместимый доступ к этим файлам. Встроенный PHP-сервер из `studio.php serve` предназначен для локальной работы.

В PHP-FPM настройте `upload_max_filesize=5M`, `post_max_size=6M`, достаточные `memory_limit` и `max_execution_time` для предпросмотра. Первый production-аккаунт создаётся через CLI под той же сервисной учётной записью:

```sh
php scripts/studio.php user-add admin --role=admin --sites='*'
```

Если TLS завершается на другом доверенном прокси, задайте FPM `STUDIO_HTTPS=1` и закройте прямой доступ к HTTP-бэкенду. Не передавайте эту настройку из недоверенного заголовка клиента.

### Подготовка статических VPS к новым редиректам

Новый deploy требует root-owned helper **`infra/apply-redirects.py`**. Для существующего сервера:

1. Установите Python 3. Скопируйте helper в `/usr/local/sbin/minicms-redirects`, владелец `root:root`, права `0755`.
2. В root-owned `/etc/minicms-deploy.json` задайте `{"web_root":"/srv/www"}` (или свой путь).
3. Через `visudo` разрешите deploy-пользователю `NOPASSWD: /usr/local/sbin/minicms-redirects *`.
4. Перегенерируйте `php scripts/nginx-config.php` и установите нужные vhost-файлы. Для хоста без сертификата используйте `--http-only`; не заменяйте его сразу HTTPS-конфигурацией.
5. Выполните `nginx -t` и reload. В vhost появится include `/etc/nginx/aigf-redirects/DOMAIN/*.conf`.

`infra/server-setup.sh` учитывает эти изменения для нового сервера, если `apply-redirects.py` лежит рядом. Он по-прежнему предназначен для ручного запуска администратором.

Helper читает только проверенную карту внутренних URL, создаёт root-owned Nginx-директивы, проверяет конфигурацию и перезагружает Nginx. Произвольный конфиг из каталога deploy-пользователя не подключается.

### Worker

Настройте SSH-ключ и `known_hosts` для сервисной учётной записи. В окружении процесса укажите `DEPLOY_HOSTS`, `DEPLOY_USER`, `DEPLOY_PORT`, `DEPLOY_ROOT`. Worker не подгружает `.env` проекта: используйте переменные окружения или systemd `EnvironmentFile`.

```sh
php scripts/studio.php worker --deploy
```

Это обработка одного задания. Для постоянной работы адаптируйте и установите `infra/studio-worker.service`, `infra/studio-worker.timer`, `infra/studio.env.example`. В шаблонах приняты пользователь `minicms` и `/srv/minicms`. Если состояние хранится вне этого каталога, скорректируйте `ReadWritePaths`. Включите timer после ручной проверки worker. Журнал: `journalctl -u studio-worker.service`.

Каждое задание строит включённые сайты и явно выбранный сайт, чтобы связанные hreflang-данные оставались согласованными. Публикация на несколько VPS последовательная; при частичном отказе другие VPS уже могут обслуживать новый релиз. Задание показывает ошибку, требуется проверить версии серверов.

Deploy блокирует одновременную замену релиза одного домена, запоминает точного предшественника и откатывается на него при ошибке активации/smoke. Удаление старых релизов происходит только после успешной проверки. Если соединение оборвалось и осталась `.deployment-lock`, сначала убедитесь, что публикация/откат не выполняются, затем вручную снимите оставшуюся блокировку. Автоматический откат без ID выбирает только релиз с `.verified`; для старого релиза до обновления укажите ID явно.

## История правок

Раньше историю держал Git: каждая публикация, каждая правка настроек и каждая цена попадали в коммит, а GitHub хранил единственную копию того, как файл выглядел вчера. Git из схемы убран, поэтому историю ведёт сама Studio — иначе публикация молча затирала бы предыдущую версию файла.

Записывается каждая запись Studio в `content/`, `config/` и `data/`: кто, когда, по какому поводу и какими были байты до. Раздел **История** показывает журнал, построчный дифф любой версии и восстановление в один клик.

Хранилище намеренно простое:

```text
.studio/history/objects/<ab>/<sha256>   содержимое файла, gzip
.studio/history/log.jsonl               журнал, только дозапись
```

Объекты адресуются по содержимому, поэтому повторная запись неизменённого файла ничего не стоит, а страница, которую правили пятьдесят раз, хранится как пятьдесят небольших блобов. Журнал — обычный текст: его можно читать через `tail`, отправлять на бэкап-хост как файл и не мигрировать при смене версии.

При первом обращении к истории делается слепок всего, что уже лежит в рабочем каталоге, — чтобы у первой же публикации было с чем сравнивать. Если файлы появились мимо Studio, на экране истории будет предупреждение и кнопка «Снять слепок».

**Восстановление** доступно администратору. Файл записывается обратно, а текущее состояние тоже попадает в историю — откат обратим. Материал с незавершённым черновиком в Studio восстановить нельзя: черновик тут же провалил бы проверку хеша при публикации, и автор не понял бы почему. Сначала завершите или верните в работу черновик.

Восстановление меняет исходник, но не сайт: на сервер изменение попадёт при следующей публикации.

`static/` в истории нет. Изображения записываются один раз под случайным именем и никогда не перезаписываются, так что версионировать там нечего — но в резервную копию они входят.

## Резервные копии

GitHub был ещё и второй копией. Без него рабочее пространство — единственная, поэтому есть отдельная команда: один зашифрованный архив исходников, истории и состояния Studio, который уезжает на второй сервер.

```sh
php scripts/backup.php key                      # отпечаток ключа и где он лежит
php scripts/backup.php create                   # локальный архив
php scripts/backup.php push --host=203.0.113.20 # создать, отправить, проверить, проредить
php scripts/backup.php verify <файл>            # расшифровать и сверить все контрольные суммы
php scripts/backup.php extract <файл>           # распаковать в .studio/recovery/<id>/
```

В архив входят `content/`, `config/`, `data/`, `static/`, `.studio/state.json` (учётные записи, черновики, очередь) и всё хранилище истории. Рабочие каталоги заданий и ZIP релизов не входят — они пересобираются.

`push` копирует архив по ssh, **сверяет SHA-256 на той стороне** и только после этого удаляет старые копии. Если сверка не сошлась, ротация не выполняется и команда завершается с ошибкой.

Расписание — `infra/studio-backup.service` и `infra/studio-backup.timer`. Хост, учётная запись и глубина хранения берутся из того же environment-файла, что и worker (`infra/studio.env.example`).

**Про ключ.** Он создаётся при первом запуске в `.secrets/backup.key` и никогда не попадает внутрь архива. Держите копию ключа не на этих двух серверах: без него архивы не расшифровать — в этом и смысл. Отпечаток печатается при каждом создании архива, чтобы можно было убедиться, что вы восстанавливаете тем же ключом.

Архив проверяется целиком: обрезанный, изменённый или расшифрованный чужим ключом файл отвергается. Проведите учебное восстановление хотя бы один раз и засеките, сколько оно занимает.
## Архивы и восстановление

Каждая успешная сборка worker создаёт `.studio/jobs/<id>/release.zip`: готовые `dist`, конфигурацию, контент, общие данные, static и шаблоны engine. Внутри — манифест SHA-256 каждого файла, в состоянии задания — хеш всего ZIP.

**Архив успешной сборки не означает успешный деплой.** Выбирайте последнее задание со статусом `published`, сверяйте ID и SHA-256 с отдельно сохранёнными данными. Файлы внутри ZIP проверяются командой:

```sh
php scripts/release.php verify /backups/release.zip
php scripts/release.php extract /backups/release.zip
```

Извлечение создаёт новый каталог `.studio/recovery/<id>/`; существующие исходники и сайты не меняются. Небезопасные пути, лишние файлы и неверные контрольные суммы отклоняются. Текущий лимит распакованных данных — 2 ГБ.

После ручной подготовки нового VPS (Nginx, helper, vhosts, TLS, SSH), из совместимого checkout движка можно отправить **готовый** проверенный релиз без повторной сборки:

```sh
MINICMS_ROOT=/srv/minicms/.studio/recovery/RECOVERY_ID \
DEPLOY_HOSTS=NEW_VPS_IP \
sh scripts/deploy-all us de fr jp
```

Укажите ID сайтов из манифеста архива. Deploy выполняет smoke-запросы прямо к IP с нужным Host/SNI. После их успеха переключайте DNS/CDN. При смене IP доменные имена в конфигурации должны оставаться прежними.

**Копии на том же сервере не защищают от его потери.** Внешнее резервирование и переключение DNS автоматически здесь не настроены. На вашей стороне остаются:

- независимое хранилище и регулярная отправка туда архивов;
- защищённый бэкап `.studio/state.json` (аккаунты, черновики, очередь), исходников `content`, `config`, `data`, `static`, версии кода и Composer lock;
- резервирование секретов/SSH-ключей отдельно с подходящим контролем доступа;
- готовый запасной VPS либо процедура его подготовки;
- мониторинг и проверка восстановления с измерением фактического времени.

Для согласованной полной копии остановите worker и запись через Studio на время снимка. ZIP релиза не содержит аккаунтов, неопубликованных черновиков, зависимостей Composer или настройки серверов. После аварии можно быстро вернуть сами сайты из `dist`, затем отдельно восстановить рабочее пространство редакции.

## Проверки и текущие ограничения

```sh
php tests/run.php
python3 -m unittest discover -s tests -p 'test_*.py'   # хелпер редиректов на сервере
php scripts/validate.php
php scripts/build-all.php --optimize
```

Браузерные проверки (Node нужен только здесь):

```sh
npm install --prefix .cache/browser --no-audit --no-fund playwright
node tests/browser.cjs
node tests/audit.cjs http://127.0.0.1:8788 <логин> <пароль>
```

На Windows используется установленный Chrome; другой путь — `CHROME_BINARY`. На Linux установите Chromium для Playwright или укажите путь к браузеру. Тесты создают изолированные копии внутри `.studio/tests` / `.studio/browser-tests` и не деплоят сайты. Скриншоты сохраняются в `reports/studio-*.png`.

`tests/audit.cjs` — не часть набора: он ходит по всем экранам в светлой и тёмной теме и сообщает о тексте ниже контраста AA, контролах без доступного имени, дублях id, `label for` в никуда, переполнении и отсутствующих фокусных кольцах. Ему нужны запущенный сервер и учётная запись.

Хранилище Studio — JSON с файловой блокировкой для небольшой команды на одном хосте. Горизонтальный кластер, SSO/2FA, редактирование несколькими людьми одновременно, планировщик публикаций, визуальное произвольное перетаскивание макета, смена пароля из интерфейса и автоматическая очистка архивов пока не реализованы. Внешние изменения исходников вызывают конфликт публикации: их нужно вручную согласовать с черновиком Studio. Действия администратора и API-события записываются в аудит, но это не отдельное неизменяемое хранилище журналов.
