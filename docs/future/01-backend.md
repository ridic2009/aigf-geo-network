# 01 — Backend Architecture

PHP 8.3 + Slim 4. Модульный монолит: границы модулей видны в дереве каталогов,
при росте модуль вырезается в отдельный сервис без переписывания.

## Структура

```
/server
  public/index.php          единственная точка входа
  src/
    Platform/               shared kernel: Config, Http, Error, Logging,
                            Validation, Database, Queue, Clock, Id, Security
    Module/
      Identity/             пользователи, роли, сессии, аудит
      Sites/                сайты, GEO, локали, шаблоны, домены, настройки
      Content/              страницы, ревизии, блоки, медиа, workflow
      Catalog/              продукты, партнёрки, авторы, цены по рынкам
      Seo/                  профили, резолвер, редиректы, hreflang, аудит
      Publishing/           задания, сборки, релизы, откаты
      Monitoring/           проверки, состояния, инциденты, алерты
  config/                   типизированная конфигурация по окружениям
  database/
    migrations/             doctrine/migrations
    seeds/                  каталог permissions, GEO, локали
  resources/
    templates/<key>/        манифест шаблона + Twig-лэйауты (build plane)
  bin/console               CLI: воркеры, миграции, обслуживание
  tests/                    Unit / Integration / Api / Architecture
  openapi/                  сгенерированная спецификация
```

Внутренняя структура **каждого** модуля одинакова — это главное правило против
хаоса:

```
Module/Content/
  Http/              Action-классы, Request/Response DTO, маршруты модуля
  Application/       сервисы сценариев, команды, Application DTO
  Domain/            сущности, value objects, enum, интерфейсы репозиториев
  Infrastructure/    реализации репозиториев (SQL), мапперы, адаптеры
  Console/           CLI-команды модуля
  README.md          ответственность модуля и его публичный API
```

## Слои и направление зависимостей

```
Http          →  Application  →  Domain
                      ↑              ↑
                 Infrastructure ─────┘   (реализует интерфейсы Domain)
```

| Слой | Можно | Нельзя |
| --- | --- | --- |
| **Http** | разобрать запрос, валидировать DTO, вызвать один сервис, собрать ответ | SQL, бизнес-правила, чтение конфига, вызов другого модуля |
| **Application** | сценарий, транзакция, вызов репозиториев, публикация событий | HTTP-детали, SQL напрямую, вывод |
| **Domain** | правила, инварианты, вычисления | фреймворк, БД, сеть, время «сейчас» (только через `Clock`) |
| **Infrastructure** | SQL, HTTP-клиенты, файлы, очередь | бизнес-правила |

### Правило межмодульного доступа

Модуль обращается к другому **только** через его публичные Application-сервисы,
перечисленные в `README.md` этого модуля. Обращение к чужому репозиторию или
чужой таблице запрещено.

Проверяется тестом `tests/Architecture/ModuleBoundaryTest.php`, который разбирает
`use`-объявления и падает при нарушении. Правило, не проверяемое машиной, — это
пожелание, а не правило.

## Ответственность компонентов

### Action (контроллер)

Один класс — один endpoint, метод `__invoke`. До 30 строк.

```php
final readonly class CreateSiteAction
{
    public function __construct(
        private CreateSiteService $createSite,
        private Guard $guard,
    ) {}

    #[Route(method: 'POST', path: '/api/v1/sites')]
    #[RequiresPermission('site.create')]
    #[RequiresStepUp]
    public function __invoke(ServerRequestInterface $request): ResponseInterface
    {
        $dto   = CreateSiteRequest::fromRequest($request);
        $actor = Actor::fromRequest($request);
        $site  = $this->createSite->handle($dto->toCommand(), $actor);

        return Json::created(SiteResponse::from($site));
    }
}
```

Разобрать → проверить права → вызвать сервис → отдать ответ. Ничего больше.

### Service (сценарий)

Имя — действие: `CreateSiteService`, `PublishSiteService`, `RevokeSessionService`.
Один публичный метод `handle()`. Владеет границей транзакции.

Классов `SiteManager` с пятнадцатью методами не существует — это god object,
который со временем становится вторым контроллером.

### Repository

Интерфейс в `Domain`, реализация в `Infrastructure`. Возвращает доменные объекты
или Application-DTO — никогда сырые массивы наружу. Методы именуются по
намерению: `findLiveByGeo()`, а не `findBy(['status' => ...])` — иначе запросы
расползаются по вызывающему коду.

### Entity

Обычный PHP-класс с инвариантами в конструкторе. Не активная запись — сущность
не умеет себя сохранять. Идентификаторы — UUIDv7: сортируемы по времени,
безопасны для показа наружу.

### DTO

`readonly final class`, только скаляры, value objects и другие DTO. Три вида:

| Вид | Где | Пример |
| --- | --- | --- |
| `*Request` | вход HTTP, здесь же валидация | `CreateSiteRequest` |
| `*Command` | вход Application | `CreateSiteCommand` |
| `*Response` | выход HTTP | `SiteResponse` |

Мапперы явные, без рефлексии: рефлексивный маппинг ломается молча при
переименовании поля.

### Value Object

Вместо примитивов там, где есть правило: `Hostname`, `Slug`, `LocaleCode`,
`GeoCode`, `Money`, `UrlPath`. Валидность гарантируется конструктором, поэтому
проверять её второй раз негде — и невозможно забыть.

## API conventions

| Правило | Значение |
| --- | --- |
| База | `/api/v1` |
| Ресурсы | существительные во множественном числе, kebab-case: `/sites/{id}/page-revisions` |
| Ключи JSON | `snake_case` — совпадает с колонками БД, меньше мест для ошибки |
| Успешный ответ | `{ "data": ... }`, для списков дополнительно `{ "meta": { ... } }` |
| Ошибка | `application/problem+json`, RFC 9457 |
| Коды | 200 / 201 / 204 / 400 / 401 / 403 / 404 / 409 / 422 / 429 / 500 |
| Пагинация | offset для коротких списков, курсор для журналов и аудита |
| Фильтрация | только whitelisted-параметры; произвольные выражения не принимаются |
| Идемпотентность | заголовок `Idempotency-Key` обязателен для publish, deploy, rollback |
| Конкурентность | поле `version` в ответе, `expected_version` в запросе → 409 при расхождении |
| Трассировка | `X-Request-Id` принимается и возвращается; он же в логах и в теле ошибки |

### Контракт

```
PHP-атрибуты на Action → openapi/openapi.yaml → openapi-typescript → client
```

OpenAPI **генерируется** и руками не правится. Клиентские типы — производная
спецификации. Расхождение контракта и реализации становится невозможным
по построению, а не по договорённости.

## Обработка ошибок

Единая иерархия в `Platform\Error`:

| Исключение | HTTP | Когда |
| --- | --- | --- |
| `ValidationException` | 422 | форма запроса неверна |
| `DomainException` | 409 | бизнес-правило нарушено |
| `NotFoundException` | 404 | объекта нет **или** нет прав его видеть |
| `AuthenticationException` | 401 | нет сессии / сессия отозвана |
| `AuthorizationException` | 403 | сессия есть, прав нет |
| `StepUpRequiredException` | 403 + код | нужно повторное подтверждение |
| `RateLimitException` | 429 | превышен лимит, с `Retry-After` |
| `ConflictException` | 409 | оптимистичная блокировка, версия устарела |
| `InfrastructureException` | 500 | БД, диск, сеть |

Один middleware конвертирует всё в `application/problem+json`:

```json
{
  "type": "https://app.internal/errors/content.page.slug_taken",
  "title": "Slug already used",
  "status": 409,
  "code": "content.page.slug_taken",
  "detail": "Slug \"candy-ai\" is used by another page on this site.",
  "request_id": "01JBX...",
  "errors": [{ "field": "slug", "code": "unique", "message": "..." }]
}
```

`code` — стабильный машинный идентификатор. **Клиент маппит код в текст**, сервер
не является единственным источником формулировок: иначе интерфейс нельзя
перевести и нельзя показать ошибку рядом с полем.

`NotFoundException` для «нет прав видеть» — намеренно: иначе 403 становится
оракулом существования объектов.

500-е наружу не раскрывают внутренности — только `request_id`; подробности в лог.

## Валидация

Три уровня, у каждого своя задача:

| Уровень | Чем | Отвечает на вопрос |
| --- | --- | --- |
| Граница HTTP | `symfony/validator`, атрибуты на `*Request` | форма запроса корректна? |
| Домен | value objects, инварианты сущностей | правило предметной области соблюдено? |
| База | NOT NULL, FK, UNIQUE, CHECK | последний рубеж: даже баг не создаст мусор |

Бизнес-проверки контента (SEO-правила, битые ссылки, дубли маршрутов) — это
**не** валидация DTO, а rule engine из [06-seo.md](06-seo.md). Смешивать их
означает блокировать сохранение черновика из-за отсутствия meta description.

## Логирование

Monolog, JSON-строки. Каналы: `http`, `security`, `audit`, `job`, `probe`, `app`.

Обязательный контекст каждой записи:

```
request_id · actor_id · session_id · ip · module · action · duration_ms · outcome
```

Процессор-редактор вырезает значения по списку ключей (`password`, `token`,
`cookie`, `secret`, `authorization`, `*_key`). Мы не полагаемся на то, что
разработчик не залогирует лишнего — мы это чиним централизованно.

| Уровень | Значение |
| --- | --- |
| `error` | требует человека |
| `warning` | деградация, разберёмся утром |
| `info` | бизнес-событие |
| `debug` | выключен в проде |

Аудит — **не лог**, а таблица в БД с ограничениями на уровне прав СУБД.
См. [04-security.md](04-security.md).

## Конфигурация

```
.env / systemd credentials → Platform\Config\* (типизированные объекты) → DI
```

* `getenv()` вызывается **только** внутри `Platform\Config`. Везде остальное —
  внедрение типизированного объекта конфигурации.
* Конфиг валидируется при старте: отсутствие обязательного значения роняет
  приложение сразу с внятным сообщением, а не на третий день в проде.
* Окружения `local`, `staging`, `production` отличаются значениями, не
  структурой. Отдельного «локального» кода нет.

## Управление зависимостями

Composer с зафиксированным `composer.lock`, `composer audit` в CI, обновление
раз в неделю.

**Правило добавления зависимости:** библиотека добавляется, только если решает
задачу, которую больно и рискованно решать самому (криптография, парсинг, HTTP),
и имеет активную поддержку. На каждую — одна строка обоснования в
`docs/adr/dependencies.md`.

## Очередь заданий

PostgreSQL, `SELECT ... FOR UPDATE SKIP LOCKED`. Воркеры под systemd.
Обоснование и альтернативы — [ADR 0007](../adr/0007-postgres-job-queue.md).

Свойства, которые это даёт: задание ставится в той же транзакции, что и
изменение данных (нет «задание есть, данных нет»); нет второго хранилища,
которое надо бэкапить и мониторить.

## Миграции БД

`doctrine/migrations`, только вперёд. Изменение со сломом совместимости
выполняется в три релиза:

```
Release N   : expand    добавить колонку/таблицу, писать в обе, читать из старой
Release N+1 : migrate   перенести данные, читать из новой
Release N+2 : contract  удалить старое
```

**Откат релиза приложения не должен требовать отката схемы.** Ни одна миграция
не делает `DROP` в том же релизе, где колонка перестала использоваться — иначе
автоматический откат из [09-ha-dr.md](09-ha-dr.md) (сценарий 11) сломает
приложение вместо того, чтобы его починить.

Каждая миграция идемпотентна и прогоняется на копии прод-базы в staging до
выката.
